# RAG 검색 방식 비교 보고서

## 1. 실험 목적

같은 Wikipedia corpus와 Solar 임베딩을 사용하더라도 벡터 유사도 계산 방식에 따라 검색 순위가 어떻게 달라지는지 비교한다. 또한 BM25 키워드 검색과 벡터 검색의 특성을 정리한다.

## 2. 실험 설정

- 데이터: `rag-datasets/rag-mini-wikipedia`의 3,200개 passage
- 문서 임베딩: `solar-embedding-1-large-passage`
- 질문 임베딩: `solar-embedding-1-large-query`
- 임베딩 차원: 4,096
- 비교 지표: cosine similarity, dot product, L2 distance
- Top-K: 5

임베딩 생성이 끝난 뒤 아래 명령으로 동일 질문에 대한 세 지표의 결과를 재현한다.

```bash
python experiments/compare_metrics.py \
  "Who suggested Lincoln grow a beard?" \
  --top-k 5 \
  --output metric_results.md
```

## 3. 지표별 의미

### Cosine similarity

두 벡터 사이의 각도를 비교한다. 벡터 크기의 영향을 제거하고 방향, 즉 의미적 유사성에 집중한다. 문장 임베딩 검색에서 일반적으로 안정적인 기준이며 본 프로젝트의 Pinecone과 Elasticsearch 벡터 인덱스도 cosine을 사용한다.

### Dot product

벡터의 방향과 크기를 함께 반영한다. 임베딩 벡터가 모두 정규화되어 있다면 cosine과 순위가 같지만, 벡터별 norm이 다르면 큰 norm을 가진 문서가 더 높은 점수를 받을 수 있다.

### L2 distance

벡터 공간에서 두 점 사이의 직선거리를 계산하며 거리가 작을수록 유사하다. 벡터가 단위 길이로 정규화되어 있으면 cosine과 순위가 거의 같아지지만, 정규화되지 않은 임베딩에서는 벡터 크기의 차이도 거리로 반영한다.

## 4. 결과 및 해석

실험 질문은 `Who suggested Lincoln grow a beard?`이며, 세 지표의 Top-5 결과는 다음과 같았다. L2는 거리가 작을수록 유사하고, cosine과 dot product는 점수가 클수록 유사하다.

| 순위 | Cosine (ID / 점수) | Dot product (ID / 점수) | L2 distance (ID / 거리) |
|---:|---|---|---|
| 1 | 382 / 0.560067 | 382 / 0.560029 | 382 / 0.937980 |
| 2 | 294 / 0.360493 | 294 / 0.360419 | 294 / 1.130819 |
| 3 | 336 / 0.342540 | 336 / 0.342659 | 336 / 1.146899 |
| 4 | 343 / 0.340425 | 343 / 0.340534 | 343 / 1.148726 |
| 5 | 302 / 0.325077 | 302 / 0.325041 | 302 / 1.161766 |

세 지표 모두 문서 `382`를 1위로 검색했다. 해당 passage에는 “Lincoln이 11세 Grace Bedell의 제안으로 1860년에 처음 수염을 길렀다”는 내용이 직접 포함되어 있어 질문의 정답 근거를 정확하게 찾은 결과이다.

또한 세 지표의 Top-5 문서 ID와 순서가 완전히 동일했다. 전체 문서 임베딩의 L2 norm을 조사한 결과 최솟값은 `0.999543`, 최댓값은 `1.000450`, 평균은 `1.000000`, 표준편차는 약 `0.000242`였다. 즉, 모든 문서 벡터가 사실상 단위 벡터로 정규화되어 있었다.

단위 벡터에서는 다음 관계가 성립한다.

```text
dot product = cosine similarity
L2² = 2 - 2 × cosine similarity
```

따라서 이번 데이터에서는 세 지표가 서로 다른 순위를 만드는 조건인 벡터 크기 차이가 거의 없었다. 실제 점수의 표현 방식은 달랐지만 문서 간 상대적인 유사도 순서는 같았고, 세 방법 모두 정답 passage를 안정적으로 1위에 배치했다. 상세 passage 미리보기는 함께 생성한 `metric_results.md`에 기록하였다.

## 5. 키워드 검색과 벡터 검색 비교

| 검색 방법 | 장점 | 단점 |
|---|---|---|
| BM25 키워드 검색 | 고유명사, 정확한 표현, 희귀 단어에 강하다. 결과 점수의 이유를 비교적 설명하기 쉽다. 임베딩 API 호출이 필요 없다. | 질문과 문서가 다른 표현을 사용하면 관련 문서를 놓칠 수 있다. 동의어와 문맥을 직접 이해하지 못한다. |
| 벡터 검색 | 표현이 달라도 의미가 유사한 문서를 찾을 수 있다. 자연어 질문과 긴 문맥 검색에 유리하다. | 임베딩 생성 비용과 저장 공간이 필요하다. 정확한 문자열이나 희귀 고유명사에서 BM25보다 약할 수 있다. 결과를 해석하기 상대적으로 어렵다. |
| Hybrid RRF | BM25의 정확한 단어 매칭과 벡터 검색의 의미 검색을 함께 활용한다. 한 방식의 검색 실패를 다른 방식이 보완할 수 있다. | 두 검색 인프라와 임베딩이 모두 필요하므로 구현과 운영이 복잡하다. 후보 수와 RRF 설정에 따라 성능과 비용이 달라진다. |

## 6. 결론

이번 실험에서는 cosine similarity, dot product, L2 distance가 동일한 Top-5 순위를 만들었으며, 세 방법 모두 정답 근거가 있는 문서 `382`를 1위로 검색했다. 이는 Solar 임베딩 벡터의 norm이 거의 1로 정규화되어 있어 세 지표가 사실상 같은 유사도 순서를 표현했기 때문이다. 따라서 현재 임베딩에는 문서 검색 지표로 cosine을 사용하는 것이 적절하고, 정규화된 벡터에서는 dot product나 L2로 바꾸더라도 검색 순위가 크게 달라지지 않을 것으로 해석할 수 있다.

검색 방식 자체를 비교하면 정확한 이름이나 표현이 질문과 문서에 공통으로 등장할 때는 BM25가 효율적이고, 질문이 문서를 다른 말로 표현할 때는 벡터 검색이 유리하다. 실제 서비스에서는 질문 유형을 미리 확정하기 어렵기 때문에 두 결과를 순위 기반으로 결합하는 Hybrid RRF가 더 안정적인 기본 선택이 될 수 있다.
