# LLM Prompting 실험 보고서

## 1. 실험 설정

- 모델: `llama-3.1-8b-instant`
- 평가 데이터: `HuggingFaceH4/MATH-500`
- 평가 문제 수: 각 실험당 50개
- Few-shot 예시: `HuggingFaceH4/MATH`의 train split에서만 추출
- 비교 방법: Direct Prompting, Chain-of-Thought(CoT) Prompting, My Prompting을 각각 0-shot, 3-shot, 5-shot으로 평가
- 재현성을 위해 `random.seed(0)`을 사용하였다.

## 2. 실험 결과

| Prompting 방식 | 0-shot | 3-shot | 5-shot |
|---|---:|---:|---:|
| Direct Prompting | 30% | 54% | 50% |
| CoT Prompting | 64% | 70% | 70% |
| My Prompting (Plan-Solve-Verify) | 56% | 54% | 0% |

실험 도중 Groq 무료 API의 분당 토큰 제한(TPM 6,000)으로 일부 요청에서 `429 Rate Limit` 오류가 발생했다. 현재 벤치마크 함수는 API 호출에 실패한 문제도 `None` 응답으로 저장하고 오답으로 계산하므로, 위 정확도에는 프롬프트의 실제 오답뿐 아니라 API 응답 실패도 포함되어 있다.

| Prompting 방식 | 0-shot 응답 실패 | 3-shot 응답 실패 | 5-shot 응답 실패 |
|---|---:|---:|---:|
| Direct Prompting | 14/50 | 12/50 | 12/50 |
| CoT Prompting | 8/50 | 6/50 | 3/50 |
| My Prompting | 10/50 | 13/50 | 50/50 |

특히 My Prompting 5-shot의 0%는 50개 요청이 모두 `None`으로 저장된 결과이므로, 프롬프트의 유효한 성능 측정값으로 해석하기 어렵다. Few-shot 수가 많아지면 예시의 문제와 풀이 과정이 입력에 추가되어 요청당 토큰 수가 증가하고, 그만큼 TPM 제한에 더 쉽게 도달한다.

## 3. CoT Prompting이 Direct Prompting보다 좋은 이유

Direct Prompting은 모델에게 풀이 과정 없이 `Answer:` 뒤에 최종 답만 출력하도록 지시한다. 출력이 짧고 빠르다는 장점이 있지만, 여러 단계의 계산이나 조건 해석이 필요한 문제에서는 중간 추론을 생략하면서 계산 실수 또는 조건 누락이 발생할 수 있다.

CoT Prompting은 문제를 단계적으로 풀고 마지막 줄에 최종 답을 출력하도록 지시한다. Few-shot 설정에서는 train 데이터의 `question`, `rationale`, `answer`를 함께 제공해 모델이 단순히 정답 형식만 따라 하는 것이 아니라 풀이의 전개 방식도 참고할 수 있게 했다. 이 방식은 다음과 같은 이유로 Direct Prompting보다 유리할 수 있다.

1. 복잡한 문제를 여러 개의 작은 계산 단계로 나눌 수 있다.
2. 중간 결과가 명시되어 계산 과정에서 빠진 조건을 발견하기 쉽다.
3. Few-shot 예시의 풀이 패턴을 새로운 문제에 적용할 수 있다.
4. 최종 답을 내기 전에 충분한 추론을 수행하도록 모델을 유도한다.

실제로 저장된 결과에서도 CoT는 0-shot, 3-shot, 5-shot 모두 Direct보다 높은 정확도를 보였다. 다만 두 방식의 API 응답 실패 횟수가 서로 다르므로 정확한 성능 차이를 판단하려면 실패한 요청을 재시도한 결과도 필요하다.

## 4. My Prompting: Plan-Solve-Verify

내가 설계한 프롬프트는 일반적인 CoT에 검산 단계를 명시적으로 추가한 **Plan-Solve-Verify** 방식이다. 모델에게 다음 순서로 문제를 해결하도록 지시하였다.

1. 문제에 등장하는 수량, 조건, 구해야 하는 대상을 먼저 파악한다.
2. 적절한 풀이 방법을 선택하고 대수 과정을 생략하지 않으면서 단계적으로 계산한다.
3. 대입, 다른 계산 방법, 부호, 정의역 및 누락된 경우를 확인해 결과를 검산한다.
4. 마지막 줄에는 `Answer: <final answer>` 형식으로 정확한 답만 제시한다.

Few-shot 예시는 test 데이터가 아닌 train 데이터에서만 추출했다. 각 예시에는 문제, 풀이 과정, 검산 지시와 최종 답을 포함하여 모델이 Plan-Solve-Verify 형식을 따라가도록 구성했다.

## 5. My Prompting이 CoT보다 좋을 수 있는 이유

일반적인 CoT는 단계별 풀이를 생성하지만, 생성된 중간 과정이 실제로 맞는지 다시 확인하도록 보장하지는 않는다. 논리적으로 자연스러워 보이는 풀이를 만들었더라도 계산 부호, 해의 조건, 경우의 수 또는 최종 답의 형식에서 실수할 수 있다.

Plan-Solve-Verify는 풀이 전에 목표와 조건을 명확히 하고, 풀이 후에는 결과를 별도의 단계에서 확인하도록 요구한다. 따라서 단순 CoT보다 다음 오류를 줄일 가능성이 있다.

- 문제에서 요구한 대상과 다른 값을 계산하는 오류
- 방정식 풀이 후 원래 식에 맞지 않는 해를 포함하는 오류
- 음수, 정의역, 중복 경우 등을 놓치는 오류
- 계산 과정은 맞지만 최종 답의 표기 형식이 잘못되는 오류

이번 저장 결과에서는 My Prompting이 CoT보다 높은 정확도를 달성하지 못했다. 특히 3-shot과 5-shot에서는 긴 풀이 예시 때문에 API 토큰 제한의 영향을 크게 받았다. 따라서 프롬프트 자체의 효과를 공정하게 비교하려면 `429`가 발생한 문제를 같은 조건에서 재시도하거나, 요청 간 대기 시간을 추가한 뒤 다시 평가해야 한다. 그럼에도 Plan-Solve-Verify의 핵심 아이디어는 단순히 추론 과정을 생성하는 데서 끝나지 않고 결과의 타당성을 한 번 더 점검한다는 점에서 CoT를 개선할 가능성이 있다.
